# 原生运行库：短按保存与消息优先级

## 原因

此前矩阵扫描只在游戏取键时发生，直接返回当次边沿，没有待消费 FIFO。
绘图期间发生的按下/松开可能完全落在两次扫描之间。更明显的是等待消息的路径：
先扫描，再阻塞于 9288 `GetMessage`，恢复时重新扫描；等待期间的短按可能已经松开。
SDK 的按键消息被丢弃以避免与矩阵重复，因此不能补回这个窗口。

另一个独立问题是 A 系列 `GuiGetMsg` 的事件优先级。用户自备 E.BIN 中 bank 8
`$5139..$51D3` 先检查/返回已到期的 `WM_TIMER`，之后 `$52CC..$52D4`
才通过 `$E7C1` 调用 `SysGetKey`。旧原生适配先消费键再处理 Timer。
游戏的非可中断动画等待可能丢弃键盘消息，返回后才以 `SysGetKey` 查询菜单输入；
反转优先级会改变这段逻辑的行为。测试以真正固件验证 Timer 返回时原键盘队列读指针不变。

## KEY-QUEUE-2 的实现

- 矩阵仍为唯一按键来源，不混合 SDK KEYDOWN/CHAR，避免一次确认触发两次。
- 16 项 FIFO 分离“捕获”与“消费”；松开不会清除已捕获的边沿；两次短按是两项。
- 在进入游戏代码之前建立启动键基线，不再等首个游戏取键调用才初始化。
- 在绘图 API 前后及每 32 个实际 LCD 字节写入处补采样；绘图不消费按键。
- CTM 分频器快速门限限制实际扫描频率，标称最多 256 Hz；不逐像素做全矩阵扫描。
- 游戏等待循环只处理已经排队的 GUI 消息，不以 `GetMessage` 阻塞等待新消息。
  A 系列 `GuiGetMsg` 仍等待游戏事件，`SysGetKey` 仍非阻塞，窗口关闭和清理协议不变。
- 恢复 Timer 优先级：先更新时间，已到期则返回 Timer，不提前弹出按键。
- 方向键首次约 312.5 ms 后连发，之后约 78 ms；队列非空时不积压自动连发。
  确认/退出不连发。超过 250 ms 未采样不能证明持续按住，重新开始连发延迟。
- 沿用原矩阵访问的短时 IRQ 屏蔽、端口恢复及仅清除新增 KEY 因子的保护。

这些修改位于通用运行库，与文件名、游戏哈希、某个地图/菜单函数无关。
framebuffer 直接映射保留，不改变游戏绘图 API 的参数或原生编译后端。

## 日志与限制

`NATIVE.LOG` 正常退出后覆盖为最新一段，标记 `build=KEY-QUEUE-2`：

| 字段 | 含义 |
| --- | --- |
| `key_scans` | 实际矩阵扫描次数 |
| `key_scan_max_gap_ticks` | 会话内最大扫描空档；真机 CTM 标称 256 tick/s |
| `key_edges` / `key_repeats` | 入队的真实按下边沿 / 自动连发 |
| `keys_consumed` | 已交给游戏的键数 |
| `key_queue_peak` / `key_queue_overflows` | 队列最高占用 / 满队列丢弃次数 |

最大扫描空档是瓶颈线索，不是按键响应时间。它包含无法采样的长计算或 SDK 调用，
调试暂停和模拟器时钟跳变也会污染这一数值。队列只能保存已经采集到的边沿；
完全发生在未采样间隙中的按下/松开无法重建，不能承诺任意长度短按绝不丢失。

这是协作式轮询，不是中断驱动输入。等待时不再睡在 GUI 消息函数中，
可能增加静止界面的 CPU 活动和耗电，需由真机评估；目前不引入未经验证的 IRQ hook。
原游戏主动忽略输入的不可跳过动画不会被强行修改为可跳过。

## 回归

宿主测试运行实际输入队列和扫描代码，覆盖松开后消费、同键两次短按、同时按键、
确认/退出不连发、方向连发、不积压连发、启动键基线、时钟回绕、长停顿、FIFO 溢出，
以及普通/等待模式均不会在空 GUI 队列上调用 `GetMessage`。
另以原固件对照 Timer/键盘同时待处理时的优先级。模拟器只用于功能验证，不据此宣称真机提速。

2026-09-05：59 项测试通过。独立模拟器中，约 50 ms 的方向键短按分别推动
《伏魔记》地图人物与《三国霸业》城池/系统菜单，每次 `key_edges` 与
`keys_consumed` 均各增加 1，无新增连发或溢出；游戏画面与 guest LCD 的
像素比对为零差异，缺失 bridge 为零。《三国霸业》的系统“结束游戏”返回主菜单。
模拟器时钟在本次运行中有整秒跳变，因此不以扫描最大间隔或模拟器速度评价真机。

## INPUT-FAIR-1：持续 Timer 过载不能无限饿死输入

2026-09-06 用户明确反馈：地图动画仍在播放，但方向键完全无响应，且《伏魔记》
与《三国霸业》同时存在。普通模拟器走图未自然复现，但受控过载测试暴露了公共
运行库缺陷：当每次 GuiGetMsg 时 Timer 都已到期，固定优先返回 Timer，根本
不取 FIFO。增加扫描频率或 FIFO 容量都不能解决此问题。

宿主测试调用实际 C 函数、排入 16 个键，旧版重复返回 Timer，键消费数为 0。
另在运行游戏的 S1C33 模拟器中，于真实 GuiGetMsg 入口强制 pending Timer，
不改游戏机器码或等待参数：旧版连续 6 次查询，注入的一个方向键一直留在队列。
这是负载条件的控制实验，并非声称已采集到真机同一位置的内部状态。

新策略只调整过载仲裁，不改变 Timer 生成频率或改成消息补发队列：

1. 一个新 FIFO 头部第一次遇到到期 Timer，仍让 Timer 先返回，按键不提前消费。
2. 该键已经让过一次，下次 GuiGetMsg 必须返回该键；Timer pending 保留到下一次。
3. 任一路径（包括 SysGetKey）取走 FIFO 头部，都清除让行标记。
   新的下一个键重新享有首次 Timer 优先，不能继承旧键的仲裁状态。
4. 没有排队按键时，Timer 行为不变；没有待处理 Timer 时，直接按原路径取键。

这是相对于 ROM 无限 Timer 优先的明确兼容性取舍：在较慢的原生适配层上避免
输入饥饿。不得宣称消息顺序在持续过载下仍逐次与 ROM 完全相同。保留首次优先的
ROM 等价测试，并以额外压力测试验证公平性及 pending 位未丢失。

`NATIVE.LOG` 的 `build=INPUT-FAIR-1` 增加：

- `timer_key_deferrals`：已捕获键第一次让 Timer 先返回的次数。
- `timer_key_yields`：第二次仍有到期 Timer 时，实际让已等待键先返回的次数。

`timer_key_yields` 非零证明触发过这条防饥饿路径，仍要结合 `key_edges`、
`keys_consumed`、`key_queue_overflows` 判断捕获/送达状况。游戏主动忽略按键的
不可跳过动画不会因此自动变为可跳过；执行单次长函数时仍可能有采样空档。

### 本次验证记录

- 65 项测试通过（配置用户自备 8.BIN/E.BIN），Ruff 与 diff check 通过。
- 实际 S1C33 强制 Timer backlog 对照：旧《伏魔记》队列计数为
  `1 → 1 → 1 → 1 → 1 → 1 → 1`；新《伏魔记》和新《三国霸业》均为
  `1 → 1 → 0`。已等待键第二次查询被消费，Timer 没有丢弃。
- 新《伏魔记》验证了地图短按移动、打开系统菜单、“退出游戏”返回标题菜单；
  未将返回标题菜单说成已退出到 9288 桌面。
- 新《三国霸业》验证了势力列表约 60 ms 短按改变选中项，并确认进入大地图。
- 两个游戏的 `c6502_missing_bridge_count` 均为零。与 FRAME-TIMING-1 相比，
  两者的 game-combined.o 分别逐字节不变；变化仅在公共运行库及链接地址。
- 真机是否完全解决同一路线的输入停滞尚待用户复测，不以模拟器性能代替真机。
