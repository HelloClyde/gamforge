# 9288 前台消息与待机保活

普通 9288 原生游戏也必须服务固件的前台协议。只扫描键盘矩阵、读硬件时钟、写物理 LCD，并不会自动取消系统的空闲计数。用户报告运行一段时间白屏，并确认是定时待机事件；此问题与 GAM 是否为 4980 格式无关。

## 独立核对 9288

2026-11-03，使用普通 9288 V1.5 固件和官方《雷霆战机》核对：

- 官方窗口使用 `GetMessage → TranslateMessage → DispatchMessage`，未处理的系统消息交给 `DefaultMainWinProc`。
- 实际 GUI 表的 `+0x64c` 指向清零空闲计数的十字节叶函数。该固件观察到的入口是 `0x0213024c`，字节为 `04 6c 77 d2 54 cf f4 3c 40 06`；这是核验记录，不是运行时硬编码调用地址。
- 此 SDK 的 `ResetAutoCloseTimer` 成员偏移是 `+0x6b8`，在该固件实际指向另一系统服务，不能按成员名直接调用。
- 9288T 恰有相同表偏移，但函数体和计数地址不同。普通 9288 必须独立校验；没有证据表明它需要 9288T 的 task 3 挂起/恢复，不能照搬。

运行时从已重定位的 GUI 表解析入口，先检查固件 RAM 地址范围及对齐，再匹配完整函数体。未知实现不试调用，会报告 `Unsupported 9288 power API`。不直接修改系统私有计数地址、不修改用户设置、不关闭系统中断或挂起后台任务。

## 运行协议

1. 创建并激活普通 GUI 窗口，等待初次 paint。
2. 验证保活入口并清零一次空闲计数，启动宿主 Timer #2，speed=1。
3. 游戏输入检查点在扫描矩阵、屏蔽短暂键盘 IRQ **之前**，服务一次有界消息批次，最多 16 条。即使队列为空，也周期性进入真实 `GetMessage`，让固件收集 IAL；宿主 Timer 只保证此接收有返回机会。
4. 分发系统消息，仍把矩阵/FIFO 作为普通 9288 游戏按键的唯一来源。GUI 按键不会再次入游戏队列。
5. 每约 128 个 CTM tick（0.5 秒）调用一次已验证的前台空闲重置；较长绘制可能延后到下个检查点，日志记录最大实际间隔。
6. 消息批次后核对并恢复直接 LCD 内容，避免 GUI/DC 提交白色系统页。维护节流从处理完成时计时，不把重绘成本叠加成连续过期轮询。
7. 收到关闭或 Quit 时先设置停止标记。C 桥接返回后再由汇编入口安全退回 `App_Main`，随后停止宿主 Timer、结束保活、释放输入和窗口。不能在回调还使用游戏栈时释放游戏状态。

游戏动画和 A 系列 Timer 仍由原来的 256 Hz 硬件 CTM 驱动，未改成 40 Hz GUI Timer 游戏循环。关闭游戏后恢复系统待机行为。

## 诊断与验证边界

`NATIVE.LOG` 增加 `host_api_verified`、`host_keepalive_calls`、`host_keepalive_max_gap_ticks`、`host_gui_pump_batches`、`host_gui_messages`、`host_gui_key_messages`、`host_gui_quit_received` 和 `host_gui_stop_requested`。这些用于判断宿主协议是否持续运行，不能视作游戏帧率。
