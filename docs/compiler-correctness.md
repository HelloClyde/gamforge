# S1C33 比较标志与帧地址代码生成修复

## 现象与证据

9288T V1.5 真机的《魔塔之怀旧终曲》首次战斗会直接重启。
两份校验有效的轮换快照属于同一会话：序号 120 已完成 `SysSaveScreen`，
序号 121 记录 `SysPicture` 进入，但没有记录返回。
对应 GAM 调用点为文件偏移 `0x2939`，矩形为 `(8,14)..(119,81)`，
源位图 `$AE82`，flag=0，大小 112×68、每行 14 字节。
日志只能定位调用边界，不包含真机异常 PC，不能单靠它断言内存耗尽或 API 错误。

用原转换产物的实际运行库对象、原位图和相同 bank 映射进行 CPU 隔离回放，
确认运行库的行输出中存在以下指令：

```asm
and  %r12, 2
cmp  %r12, 0
ld.w %r12, %sp
add  %r12, 28
jrne alignment_prefix
```

`ADD` 覆盖了 `CMP` 的 PSR。该矩形首行 framebuffer 指针本应为 `0x003c0ad4`，
已经四字节对齐，却错误进入半字前缀，随后从二字节对齐的 shadow 地址执行字访问。
原对象在 CPU 回放中因此发生对齐异常。隔离环境的异常位置不是实测真机故障 PC。
这里读的是已载入的资源，绘图路径没有新申请堆内存；不能把此次复现归因于图片读盘。

## LLVM 根因

固定上游源码的 `S1C33InstrInfo.td` 将 `ADJFI` 视为不改标志的帧地址伪指令，
却在 `S1C33RegisterInfo.cpp` 的 frame-index elimination 中展开为 `LD SP + ADD`。
展开发生在调度之后，漏报 PSR 依赖便可能让它落入比较与条件跳转之间。

仓库工具链补丁给 `ADJFI` 增加 `Uses = [SP]`、`Defs = [PSR]`，
让未来重建的 LLVM 在调度阶段看到真实依赖。
此次用于游戏构建的现有 Windows LLVM 二进制没有被替换；实际修复依靠下述兼容层。

## 转换器通用修复

所有输出机型的 C 运行库都先生成汇编，再经 `preserve_comparison_flags` 处理后汇编：

- 保护同一直线 `CMP → 条件跳转` 区间内的 `LD Rd,SP → EXT* → ADD Rd,常量` 帧地址展开。
- 保存、恢复完整 PSR，保留 R0 结果、其他寄存器与原 SP，不使用固件保留的 R15。
- 临时占用两个栈字，计算地址时补偿八字节。所有 EXT 前缀与消费者保持绑定。
- 普通算术、不同目标寄存器、动态 ADD、调用和新标签终止匹配；不保护需要自己生成分支标志的算术。
- 9288T 保留既有的预览 CPU 加载标志兼容；9288 / S / 600 不额外保护这些加载。
- 手写的原生游戏汇编和快 ABI helper 不经过 C 伪指令展开，保持既有代码路径。

同时修正旧兼容层的 SP 寻址补偿：无 EXT 时，SP 的 imm6 按字/半字/字节访问宽度缩放；
有 EXT 时，完整位移是**字节数**。跨过无 EXT 的范围时必须切换编码，不能仍把位移当成字数。

这是公共代码生成修复，不检查游戏名称、GAM 哈希或战斗场景签名，不引入解释器回退。

## 回归

实际 S1C33 CPU 微程序检查比较结果、完整 PSR（含 IE）、R0 作为目标、SP 恢复，
以及 252/256/380 字节等边界处的字、半字、字节 SP 访问。

`scripts/verify_picture_codegen.py` 链接转换器实际生成的运行库对象，
仅把 `native_picture` 变为可从测试入口调用的符号，不替换或手改绘图指令。
它与独立逐像素参考输出比较完整的 9,600 字节 framebuffer，并检查 RAM 前后保护区和 SP。
测试既使用用户原位图，也使用纯生成的合成数据；仓库不包含游戏资源。

```powershell
$env:PYTHONPATH = 'src'
python scripts/verify_picture_codegen.py `
  --runtime-dir '转换工作目录/c6502-native-runtime' `
  --toolchain '工具链根目录' --emulator 'c33emu.exe路径' `
  --game '用户的魔塔.gam' --output-dir 'build/picture-replay' `
  --rect '8,14,119,81' --rect '0,14,111,81' --rect '16,14,127,81' `
  --rect '1,64,112,66' --rect '8,65,119,65' --rect '152,95,158,95'
```

该工具限定 9288T 1×、数据 bank 9..12 连续、flag=0 的 ROM 位图路径。
默认数据 bank 为 `$21D..$220`，源地址 `$AE82`；其他位图可以用参数指定。
它不是完整固件 UI 回归，输入与追踪文件系统均不参与，也不是性能测试。

本次结果：六种矩形均正常返回，完整 framebuffer 零差异，RAM 保护区和 SP 正确。
首次战斗的参考画面 SHA256 为
`218ee67e45524671683af66071c516443fdf4b4169f5f00d009c21038dde5664`。
启用实际工具链、CPU 核及修复后运行库的全套回归为 **319 项通过**；
9288 / T / S / 600 的实际转换均完成。
pytest 的生产绘图对象回归需要设置 `A9288_TEST_T_RUNTIME`，
指向新转换的 `c6502-native-runtime`；CPU 测试还需 `A9288_TEST_CLANG`、`A9288_TEST_C33EMU`。

真机首次战斗是否不再重启，仍需用户用新 EXE 复测。
此次没有验证所有游戏、所有外置资源路径，也没有声称所有 LLVM 后端问题已经解决。

## 2026-10-14：非默认入口与公共菜单/LCD 运行库

用户提供的《中国象棋.gam》在代码翻译后被显式接口检查拒绝：缺少
`GuiMenu`、`SysLCDClear`、`SysPictureFill`、滚动条与上下箭头三个接口以及
`C6502_SUB16`。补齐后又暴露了构建器固定调用文件偏移 `$0046` 的问题；
该文件头的启动 PC 实为 `$5047`，对应文件偏移 `$0047`。

通用修复：

- 启动桥从 GAM 头读取入口，生成相应的 S1C33 原生函数调用，不再写死 `$0046`。
- 按 A 系列 `dictsys.h` 的紧凑结构和 16 位指针实现原生菜单；不能把客机菜单结构
  强制转换成 9288 SDK 的宿主结构。游戏内仍独立轮询按键，不引入 GUI 消息循环。
- 菜单覆盖多列、图标、循环选择、上下左右、翻页、数字快捷选择及退出焦点回写。
  空菜单、零列和无效显示区域在访问数组前拒绝，不复现固件的越界绘图。
- `SysLCDClear` 清除完整 LCD 存储包络；`SysPictureFill` 写 96 行紧密位图，
  保留每行尾部属于硬件图标的低位。滚动条和箭头修改对应客机图标位，
  这些位不在 159 像素游戏视口内，不能当作游戏像素放大。
- 16 位加减法必须保留**最后一次高字节 ADC/SBC** 的 N/Z/C/V，而不是只存结果。
  低字节写入后再读取高字节操作数，保留重叠零页变量的顺序；`$28/$29` 仍使用
  寄存器常驻软件栈，PHP/PLP 模板则保留原状态与 lazy NZ。

`tests/test_menu.py` 用合成数据回归：512 组算术与 65C02 参考执行对照；
63 组菜单按绘制调用、返回值、环境结构和键盘状态与原 E.BIN 对照；
全屏清除/填充、256 个滚动百分比和箭头状态核对 LCD RAM 字节。
ROM 对照需要用户提供 `A9288_ROME`，不把游戏或固件复制进测试夹具。
固件 API 表用于解析实际目标，不使用另一版 `test.map` 的物理函数地址硬套。

这解决了该 GAM 的转换失败；PC 等价回归和生成 KF2 并不等于真机整局游玩验证。
