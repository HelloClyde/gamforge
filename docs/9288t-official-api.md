# 9288T 官方程序的 API 调用对照

## 调查范围与证据

2026-10-11，对照从 9288T 模拟器镜像提取的官方《伏魔记》，调查转换版
《魔塔之怀旧终曲》在真机 V1.5 首次战斗直接重启的问题。
这是静态反汇编和源码对照，**尚未复现战斗异常，不能据此宣布重启已修复**。

本次不是拿 9288 或 9588 的程序推测 T 的接口：

- 官方 `official-fumo.exe`：801,181 字节，SHA-256
  `0487c9a0ddcca4f383d020f662039c79393426c19d59744133e772eaaa5900e0`。
- 9288T 固件 RAM 转储：基址 `0x02000000`、长度 `0x200000`，SHA-256
  `c3cb49b427165a5365d328ee72e177fad0f3bc28eb0e701b8eea17874a609e15`。
- SDK：本地 `bbk9288-app-env-upstream` 的 `include/RT_table/RT_GUI.h`、
  `RT_OS.h`、`RT_FS16.h`，对应提交 `eae216c`。成员偏移通过实际
  S1C33 Clang 编译 `__builtin_offsetof` 得到，不按注释或手工数行推导。
- 对照产物：`build/9288t-games/gamforge_9288T_魔塔之怀旧终曲.exe`，SHA-256
  `5edb3915bd37ee6ef1d761e543e04f19e7bb73f6a690ce8f36f9233eaefea00e`。

固件函数地址只标识本次样本，不可硬编码进应用。真机照片里的 V1.5
也不能单独证明所有函数表项和该模拟器固件一致。官方二进制、转储和游戏不提交到仓库。

## 1. 启动、窗口与宿主 ABI

官方 KF2 的 code_offset 为 584，total_size 为 99,604，装载到
`0x02700000` 的部分为 99,020 字节。文件其余 701,577 字节是追加数据，
不能把整个 801,181 字节都当作运行时装载镜像或代码。

官方启动入口的顺序为：

```text
0x02700000 → 初始化重定位表（0x02700014）
           → 初始化 C 运行库（0x0270005e）
           → App_Main（0x0270bbce）
```

它从系统总表 `0x02000200` 取得 ROS33 / GUI / FS / CRTL 等指针，
没有在这个启动入口另设 SP 或关闭 IRQ。当前翻译器同样取得这些表指针，
不能据此要求游戏随意换栈、接管系统或使用另一机型的表地址。

官方调用使用 GNU33 ABI：前四个参数 R6–R9、返回 R4，更多参数放在调用者栈上。
例如下面的 `fread` 在 `CALL.D` 的延迟槽才设置 R9，这是在进入被调函数前执行，
不是遗漏 FILE 参数。分析时必须把延迟槽纳入调用现场。

窗口调用：

| 官方调用点 | 表项 | 含义 / 参数 |
| --- | --- | --- |
| `0x0270bbf6` | GUI + `0x84` | CreateMainWindow，R6 指向栈上的创建结构 |
| `0x0270bc0e` | GUI + `0x88` | DestroyMainWindow，R6=HWND |
| `0x0270bc1c` | GUI + `0x17c` | MainWindowCleanup，R6=HWND |
| `0x027140fa` / `0x02714108` | GUI + `0x50` / `0x54` | TranslateMessage / DispatchMessage |
| `0x02714134` | GUI + `0x30` | GetMessage，R6=消息结构，R7=0 |

官方创建窗口后检查返回值 `-1`；SDK 的 `HWND_INVALID` 也是 `0xffffffff`。
调查时的 `c6502_native_9288.c` 只检查 `!window`，这是一个失败路径检查缺口；
后续修复已同时检查 `HWND_INVALID`。
它发生在启动阶段，**不是已证明的首次战斗重启原因**。
官方与当前运行库的主循环结构不同，不能照抄官方未过滤 GetMessage 的退出流程；
现有翻译器仍需保留已验证的应用窗口过滤、按键释放和桌面恢复协议。

## 2. 文件与资源读取

官方 `0x0270bd74` 附近实际执行：

```c
fs_fseek(file, -4, SEEK_END);       /* FS + 0x10 */
fs_fread(local_buffer, 4, 1, file); /* FS + 0x08 */
fs_fclose(file);                   /* FS + 0x04 */
```

`fread` 调用现场：R6=目标缓冲，R7=4，R8=1，R9=FILE。
官方随后重新打开文件并处理追加资源。当前运行库使用相同 FS 表的参数顺序；
没有在这里发现 `size/count/FILE` 搞反的问题。

转换版魔塔是 `external_resources=false`，启动时完整解压 81,559 字节 GAM 到 RAM。
其战斗资源不走外置 RES 缺页读取。但游戏存档仍可能使用文件 API，
不能进一步声称游戏运行期间绝无文件调用。

官方 CRTL + `0x00` / `0x04` 为 malloc / free。当前版使用同一表，
本次未发现分配 API 槽位或前四参数 ABI 错用。当前魔塔装载镜像约 281 KiB，
游戏分配约 80 KiB，桌面备份 9,600 字节；这些数据不足以判定 RAM 耗尽，
也没有测出 9288T V1.5 的堆上限。此前 9288 的约 1.5 MiB 反馈不能当成 T 的结论。

## 3. 绘图：后段偏移与真实参数

官方调用与固件实现确认的图形表项：

| 接口 | SDK 成员偏移 | 本样本实际 GUI 偏移 | 证据 |
| --- | --- | --- | --- |
| SysShowPicV | `0x58c` | `0x5a0` | 官方调用 `0x02713bf4` |
| SysShowPicS | `0x590` | `0x5a4` | 官方调用 `0x02713ca4` |
| SysBltFrame | `0x59c` | `0x5b0` | 官方调用 `0x027142de`；固件 `0x02104504` |
| SysHz | `0x5a4` | `0x5b8` | 固件 `0x0210464e`，16 位字码 |
| SysPrintString | `0x5a8` | `0x5bc` | 固件 `0x02104754`，逐字节遍历字符串 |

前两项的完整参数为：

```text
SysShowPicV:
  R6=x, R7=y, R8=width, R9=height
  caller stack[0]=picture, [1]=VirtualScr, [2]=mode

SysShowPicS:
  R6=HDC, R7=x, R8=y, R9=width
  caller stack[0]=height, [1]=picture, [2]=mode
```

官方包装函数 `0x02713bcc` 将 A 风格的结束坐标转换为
`width=x1-x+1`、`height=y1-y+1` 后才调用 SysShowPicV。
不能把结束坐标直接当作宿主 width / height，也不能混淆 V 接口与 S 接口的 HDC 参数。

当前翻译器只用该后段 API 来生成字形；位图和最终显示主要由自身原生绘制和
framebuffer 映射完成。已检查魔塔实际生成的汇编：SysPrintString 从 GUI + `0x5bc`
取得，R6=桌面 HDC、R7/R8=0、R9=单字字符串，第五参数为宿主大小的暂存画面。
**不是把 1,920 字节客机单色显存直接传给宿主字形 API。**

所以当前 `SysPrintString +0x14` 有实际固件证据，不应因这次重启而退回 SDK 原槽位。
这里没有确认战斗过程的实际调用序列，字形缓存未命中时的运行状态仍需另行跟踪。

### 官方整帧提交顺序

`0x027142b6` 的一个分支实际为：

```text
SetInstantPaint(1)                  GUI + 0x74
SysBltFrame(HDC, VirtualScr)        GUI + 0x5b0
SetInstantPaint(0)                  GUI + 0x74
SysBltFrame(HDC, VirtualScr)        GUI + 0x5b0
```

其他绘图包装路径（例如 `0x0271428a`）调用
`InvalidateRect(HWND, NULL, 0)`，即 GUI + `0xe0`。
官方维护 GUI 画面并提交到显示系统，不只是独立写 VRAM。
当前直接 framebuffer 映射是另一条已经存在的输出路径；是否有系统画面竞争
值得做独立对照，但**显示流程不同本身不能证明会重启**。

## 4. 进入 / 退出游戏：系统任务 3

这是本次新发现的明确协议差异，不是根据 SDK 名字猜测：

```text
官方 0x0270bc32 调用 GUI + 0x6f4
  → 固件 0x020f7a3e
  → ROS33 + 0x24 的 ros33_sus_tsk(3)，实现 0x02176c24

官方 0x0270bc94 调用 GUI + 0x6f8
  → 固件 0x020f7a48
  → ROS33 + 0x28 的 ros33_rsm_tsk(3)，实现 0x02176c96
```

两处包装函数均在延迟槽把 R6 设置为 3。ROS33 + `0x24/0x28` 也与
9288T SDK `RT_OS.h` 的 sus_tsk / rsm_tsk 成员偏移一致。
固件 `0x020f4a58–0x020f4a6c` 创建任务 3，入口 `0x02139e82`。
该入口包含 `0x00300f20` 等设备访问、事件等待及数据处理，
本次未完整恢复其职责，不直接命名为键盘、看门狗或某个通信服务。

当前翻译器没有这一对挂起 / 恢复调用，运行期间仍让该系统任务存在。
但这**不是关闭全部调度，不是关中断，也不是 DisableKeyBoard**。
不要在游戏运行中调用 9288T SDK 的 `EnableKeyBoard` 原槽位 + `0x600`：
本样本该位置指向 `0x02137080`，实际只是读取 `0x00003fe8` 的一个字节，
明显不符合启用键盘的动作语义。给该槽位简单再加 `0x14` 也未得到键盘控制函数。
T 当前使用私有矩阵轮询，S 的键盘服务用法不能直接套用到 T。

如果后续做官方生命周期对照，应优先通过已经核实的 ROS33 表调用，
记录挂起返回值，并只在本次挂起成功后执行配对恢复；恢复必须先于重回 GUI 消息循环。
还需测试是否与文件 / SDK 调用互相依赖、退出后桌面和输入是否正常。
**本次没有把未经场景验证的任务挂起操作加入交付 EXE。**

## 5. 对首次战斗重启的判断

这轮没有找到“资源读取用了另一个机型 API”或“SysPrintString 参数数量用错”的证据。
也没有证据把重启直接归因于 9288T 堆容量不足。

接下来应分开验证，而不是把几个差异一起改掉再猜：

1. 记录首次战斗的最后一个原生调用、宿主 SP 高水位、失败分配及非法访问位置。
2. 检查该路径的 C6502 长整数 ABI。之前 ROM 等价检查已经发现
   `__uns_div_long` / `__cmp_long` 等返回状态存在缺口；这是客机运行库翻译问题，
   与宿主 FS / GUI 接口不是同一层。
3. 对照官方任务 3 挂起 / 恢复及 GUI 表面提交协议，独立做 A/B 场景测试。
4. 在模拟器复现前，静态调用匹配不能替代真机 V1.5 首次战斗验证。

本次仅记录逆向结论；没有改动游戏运行时、发布修复 EXE、push 或 release。
