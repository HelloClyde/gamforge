# 9288T 16 灰阶独立实验

`9288T_16GRAY_PROBE.exe` 是独立 LCD 模式探针，不是已经支持 16 灰阶的游戏运行库。
生产游戏仍保持系统原生的 2bpp / 四灰阶模式。16 灰效果、物理 LCD 响应和完整固件退出
需要在对应 9288T 真机上确认，CPU 模拟通过不能代替这些结论。

## 使用

1. 启动实验 EXE，普通应用窗口约一秒后自动开始。
2. 先显示四灰阶纹理约三秒，再显示十六灰阶纹理约三秒；顶部是对应灰阶条。
3. 自动恢复原 LCD 模式、LUT 和画面，然后显示结果页，约两秒后关闭返回。
4. 查看 `A:\GRAY16.LOG`，每次只保留最新一次。

实验显示期间关闭 CPU IRQ，不能通过按键退出；正常硬件时钟下总计约六秒。
每段另外有 256 帧硬上限，时钟没有推进也会结束。此模式专为隔离 LCD 格式验证，
不代表生产游戏会关闭中断运行，也不验证睡眠唤醒。

`status=1` 仅表示程序完成模式切换并通过恢复值比较；不自动证明肉眼可辨 16 灰。
`status=2` 表示 DMA 通道仍使能，未修改 LCD；`3` 表示初始深度不是 2bpp；
`4` 表示面板布局不是 240×160；`5` 表示恢复值比较失败。
`gray4_timed` 和 `gray16_timed` 为 1 表示达到三秒目标，为 0 表示帧数上限先到。
比较吞吐可分别计算 `frames * 256 / ticks`，不要把它解释成游戏 FPS。
使用日志头 `PROBE 3` 的版本。它记录任务 3 的 suspend/resume 返回值、事务前后的
PSR 与 R15/DP，便于区分 LCD 恢复和完整系统恢复。

## 边界与恢复

地址来自 9288T SDK 的 `c33L05.h`：

| 项目 | 地址 |
| --- | --- |
| LCD 模式 | `0x00380200` |
| 显示起始地址 | `0x00380210` |
| LUT | `0x00380400` |
| 显存 | `0x003c0000` |
| CTM 自由计数器 | `0x00040153` 起 |

先按官方程序创建自己的主窗口、消息循环与焦点，再按官方游戏使用的 ROS33
任务 3 挂起/恢复配对进入实验。
先保存 PSR，关闭 IRQ，再检查四个 HSDMA 通道未使能；不强制停用任何 DMA 通道。
保存完整 19,200 字节覆盖区、前 16 项 LUT、mode 和 start。仅改变 BPP、LUT bypass
及临时 blank 状态，保留面板驱动参数、时序、反相设置和尺寸。
退出按 blank → 原显存 → 原 LUT/start/mode 的顺序恢复并比较，最后恢复 PSR。
所有 GUI 和文件系统调用均发生在这段事务以外。

实验不会修改 IRAM、Timer、TTBR 或看门狗。未假设看门狗已经被关闭；因此它仍是
待真机验证的硬件实验，不应直接移入长时间游戏会话。

## 缩放与测量

两条路径处理相同 159×96 单色源，目标 239×144，中心采样 `(4*d-1)/6`、边界夹取。
四个垂直权重阶段各用 64 项表，将两行的 3 位源一次变成 3 个目标像素；总表量 1 KiB。
运行时无浮点和插值除法，每行先组合像素再按字节写显存。忽略源第 160 个隐藏像素。
顶部渐变和原始纹理生成的成本也包含在本探针的计时里。

S1C33 CPU 独立测试结果（不含固件竞争或真实外部 RAM 等待）：

| 独立测试 | CPU 周期 | 结果 |
| --- | ---: | --- |
| 4 灰完整纹理和渐变 | 800,119 | 与独立逐像素参考逐字节相同 |
| 16 灰完整纹理和渐变 | 926,742 | 与独立逐像素参考逐字节相同 |
| 有限事务和完整恢复 | 5,354,500 | mode、start、LUT、19,200 字节显存均恢复 |
| 实验会话生命周期 | 5,354,584 | 任务 3 恢复一次、FS 仅在 2bpp、R15 保持 |

后两项人为设置每段两帧，CTM 不推进，验证备用退出上限；生命周期测试的任务/FS API
为 mock，LCD 和显存事务在实际 CPU/MMIO 中执行。GUI 创建、消息与退出必须由完整固件验证。
四项均正常 HALT，没有异常或未知访问。
四灰对比路径是同一实验内核，不是生产游戏当前的高度优化内核，
不能据 15.8% 差值断言改成 16 灰会让整款游戏慢 15.8%。

### PROBE 1 退出问题修复

首版完整固件试运行的两阶段绘图与 LCD 恢复通过，但结果框之后不能正常返回。
检查实际 S1C33 汇编发现：事务被内联进 App_Main 后，编译器将任务挂起结果的
`CMP` 放在 `LD PSR` 前，将依赖比较标志的 `JRNE` 放在其后。恢复 PSR 覆盖比较结果，
因此可能跳过必须执行的 `rsm_tsk(3)`。

PROBE 2 将事务设为 noinline，并为所有 PSR 写入声明 `cc` clobber。
新汇编先 `CALL run_probe`，返回后重新读取任务结果并 `CMP/JRNE`。
新增生命周期回归验证挂起成功时一定恢复一次；保留真实固件验证边界，不能把
“LCD restored=1”理解为“已经正常返回桌面”。PROBE 1 不应交付。

完整固件试运行 PROBE 2 时曾观察到画面仍停在首次 MessageBox，未取得本次新日志，
当时未确认它已进入 LCD 事务或正常退出。CPU mock 不覆盖这条 GUI 路径，不能据此称为
完整验证通过；`unknownAccesses=6` 是启动历史，不能用累计值或一次 PC 采样证明这次
探针发生了新异常，也尚无证据将现象归因于 MessageBox、窗口上下文或 API 槽位错误。
PROBE 3 改用更便于自动验证的普通主窗口流程，移除两处模态确认：
CreateMainWindow → 本窗口 GetMessage/TranslateMessage/DispatchMessage →
DestroyMainWindow/PostQuitMessage/MainWindowCleanup。结果页采用普通窗口自动结束，
所有系统绘图仍在原始 2bpp 模式。这是生命周期简化，不宣称已找到此前现象的根因；
需再次由完整固件证实退出。

### GUI 表项核对

按实际 S1C33 编译结果，TextOutLen 是 GUI `+0x4f0`；官方伏魔记的
`0x02713764`、`0x0271378c` 也使用此槽，R6–R9 是 DC/x/y/text，第五参数
len 在栈上，`-1` 表示字符串长度。该固件表槽指向 `0x02110f0e`，实现读取第
五参数并在其为负数时计算字符串长度，确认此段不需要游戏字形后段的 `+0x14`。
代码中加入了 TextOutLen、CreateMainWindow `+0x84`、MainWindowCleanup `+0x17c`
的编译期偏移检查，应用仍从实时重定位表取入口，不硬编码固件函数地址。

旧版 MessageBox 的 SDK 槽 `+0x2b8` 也与官方伏魔记 `0x02714024` 的调用一致，
不能将此前现象解释成沿用了错误晚表偏移。

2026-10-15 首版在隔离 NAND 的完整 Dream9288T 固件中从桌面启动：
`status=1`、`restored=1`，四灰 31 帧 / 772 tick，十六灰 28 帧 / 768 tick，
两个 `timed` 均为 1，测试结束显示恢复提示，但首次完整固件验证发现结果提示
无法关闭，尚不能视为正常返回桌面。`restored=1` 仅覆盖显存及 LCD 寄存器比较。
这不证明真机面板能分辨 16 灰，
也不验证生产游戏中 GUI、DMA 和睡眠唤醒与 4bpp 的长期共存。

### PROBE 3 完整固件复测

2026-10-15 的完整固件复测使用 `PROBE 3`，EXE SHA-256 为
`8bc03d108de45c581a988b0dea42b32a0cea300a84fd5c91d100a9c337492fd7`。
日志为 `build/9288t-gui-validation-20261015/GRAY16-PROBE3.LOG`：

| 检查 | 结果 |
| --- | --- |
| LCD/显存恢复 | `status=1`、`restored=1` |
| 任务 3 挂起/恢复 | 返回值均为 `0` |
| PSR / DP | `16 → 16` / `0 → 0` |
| 四灰阶段 | 29 帧 / 788 tick，达到计时目标 |
| 十六灰阶段 | 27 帧 / 781 tick，达到计时目标 |
| 应用退出 | 结果页自动结束，显示系统桌面，时钟继续运行 |
| 桌面输入 | 右键使选择光标从 C 移至 D；数字分类切换尚未确认 |

这是完整固件中的生命周期观察，不再只是 CPU mock。没有加入猜测性的 launcher
焦点补丁：官方伏魔记 `0x0270bbce` 的退出顺序是 DestroyMainWindow、
MainWindowCleanup 后返回；现有 9288T 游戏运行库也不强制恢复 launcher 焦点。
探针最终复制桌面到前台显存的行为与该运行库相同，不能据此断言输入恢复故障。

目前抓取的图像最多只统计到 4 种颜色，尚未得到可以证明实际显示出 16 级灰的画面。
因此只确认程序尝试了 4bpp、恢复比较通过以及上述桌面响应，不宣称模拟器或真机
已显示完整 16 灰。真实面板灰阶、物理设备性能、数字分类切换及睡眠唤醒仍需验证。
两阶段帧数是本探针的纹理生成加插值写入吞吐，不是游戏帧率，也不能外推真机增益。

构建：

```text
python scripts/build_9288t_gray16_probe.py --sdk <sdk9288t> --toolchain <toolchain>
  --output-dir <temporary-build-dir> --output 9288T_16GRAY_PROBE.exe
  --emulator <c33emu.exe>
```

输出目录包含原始 ELF、二进制、编译后的汇编、独立 CPU framebuffer 和 `report.json`。
输入仅为 SDK/工具链与程序自生的纹理，不需要或分发任何 GAM 游戏资源。
