# 9288T 输出适配

这是输出目标扩展：输入仍为 A 系列 C6502 GAM，PC 离线生成 S1C33 原生代码。
不解释 9288T EXE，也不改变 GAM 的逻辑、Timer 参数或 guest 显存布局。

## 机型差异

| 项目 | 9288 | 9288T |
| --- | --- | --- |
| CLI 目标 | `--target 9288`（默认） | `--target 9288t` |
| SDK 头文件目录 | `Down_Include` | `include` |
| LCD | 320×240 / 80 字节每行 | 240×160 / 60 字节每行 |
| 显存字节数 | 19,200 | 9,600 |
| 游戏显示 | 2×，318×192 | 默认 1×，159×96；可选 1.5×，239×144 |
| 左 / 上边距 | 1 / 24 | 1× 为 40 / 32；1.5× 为 0 / 8 |
| KF2 娱乐字段 | `0x0008` | `0x0208`（当前支持的固件启动格式） |
| 图标样式 | 保留系统白框，内嵌 30×30 图片 | 原图适配 40×40，不添加 9288 白框背景 |
| 后段 game GUI 表修正 | V1.5 `+0x14` | 当前模拟器固件字形段 `+0x14` |

两机均以 `0x02700000` 加载，应用地址窗口至 `0x02800000`，
使用 GNU33 的 r6–r9 参数 / r4 返回 ABI；framebuffer 基址为 `0x003c0000`。
不能只修改 KF2 字段：行跨度、字形暂存、桌面备份及输入适配均需同时切换。

9288T SDK 核对来源：本地 `bbk9288-app-env-upstream`，提交 `eae216c`，
上游 `https://gitee.com/BBK_9288T/app_env`。其 demo 定义 240×160；
`apmk/gen_ap_kf2.c` 标明适用于 9288/T。模拟器自带伏魔记与 BB 虚拟机
EXE 均为 machine=1、module=`0x0208`，BB 虚拟机使用同样的 40×40 / 16×16 图标格式。
SDK `gen_ap_kf2.c` / Makefile 默认使用普通分类号，但当前支持固件的
`A:\系统\程序` 启动入口按 `0x0208` 查询程序。仅把新文件放进此目录，也不等于
更新固件的应用目录。相同文件在既有入口下用 `0x0008` 可显示图标，却在实际加载时
被程序类别查询拒绝；不能把图标显示当作启动验证。本目标恢复使用已验证的 `0x0208`，
不改变 9288 的 `0x0008`，也不声称该标志在其他固件下含义相同。
这些依赖不提交到源码仓库。

### SDK 后段表校正

官方《伏魔记》的实际调用点、栈参数、文件接口和进入 / 退出游戏协议，
详见 [9288T 官方 API 对照](9288t-official-api.md)。其中 GUI + `0x6f4/0x6f8`
已追到系统任务 3 的挂起 / 恢复，不能当成键盘启停接口；
这项差异目前是兼容性调查证据，不是已通过回归的运行库变更。

2026-10-14 的 `T-HOST-1` 进一步核实官方 GUI `+0x64c` 空闲计时重置入口，
并落实了上述任务 3 的配对生命周期及前台保活。它使用独立核验，不沿用字形段的
`+0x14` 修正；未知接口拒绝启动，详细证据和真机验证边界见官方 API 对照第 6 节。

不能把原 SDK 的后段布局直接用于这一固件。用 S1C33 Clang 的 `offsetof` 实测：
`SysPrintString` 为 `0x5a8`，`ScanKeyForGameComboKeys` 为 `0x68c`。
GUI 表必须通过系统重定位表取得，不能硬编码其 RAM 地址；启动状态改变后
表基址会变化。当前固件转储的 `GUI+0x5bc` 指向 `0x02104754`，
反汇编可见字符串遍历；`GUI+0x5b8` 指向 `0x0210464e`，使用 16 位字码。
因此字形段比 SDK 多五项，运行库按 `+0x14` 修正。早段窗口 / DC / 消息
函数不加。之前按旧表基址推导的 `+0x10` 是错误结论，已撤回。

不能将这个修正套到表尾的按键函数：当前固件 `GUI+0x69c` 是其他服务，
并非 `ScanKeyForGameComboKeys`。本适配不调用此未确认的 SDK 入口。

## 图形与输入

两机图标仍为 40×40 / 16×16 四灰阶。9288T 的默认图标仅使用内层图案，
自选图标保留原图内容与比例，不额外套框；切换目标时预览同步更新，并与 KF2 资源一致。

保留 guest 159×96 单色显存，默认 **1× 点对点**：每个 guest 像素只占一个物理像素，
画面居中于 x=40、y=32，左右留白 40/41 像素、上下各 32 像素。字形和地图格子不做重采样。
256 项展开表将一源字节变为两字节 2bpp 像素，独立写入用半字，连续行段按对齐字融合；
完整一屏正常绘图只写 3,840 字节。第 160 个隐藏像素仍为白色，不改 guest RAM。

GUI 的“画面缩放”保留 `1.5x` 可选模式，CLI 用 `--display-scale 1.5x` 选择。
它将一源字节展开为 12 个物理像素（3 字节），像素和行交替占 2 / 1，
最终画面 239×144，右侧 1 像素白边。此模式线条粗细不均是非整数缩放的结果。
模式在转换时确定，不是已有游戏 EXE 内的设置，旧产物需重新转换；9288 仍固定 2×。
屏幕审计比较物理字节，正常 guest 写入立即更新目标 framebuffer，仍不依赖 present 才可见。

`build=T-SCALE-1` 日志记录 `display_scale_numerator/denominator`、`display_x/y`；
转换报告记录 `display_scale`、`display_width/height/x/y`。
全屏白边、无通知 GUI/DMA 覆盖恢复、原始 RAM 修改、部分行遮罩和折行均沿用屏幕审计。
三种 T 模式各自编译，不在每个像素上增加运行时模式判断，也不改变游戏 Timer 或输入时序。

### 四灰阶双线性放大

GUI 选择 `1.5x-linear`，或 CLI 添加 `--target 9288t --display-scale 1.5x-linear`。
这是真正的水平、垂直四点双线性插值，不是最近邻缩放后加一层抖动。
源仍为 159×96 单色；目标仍为 x=0/y=8 的 239×144 区域，右边第 240 像素保持白色。
按像素中心映射 `(4*d-1)/6`，边缘夹取源像素，两方向加权后只量化一次为 0/1/2/3。
隐藏的源第 160 位不参与插值，不修改游戏显存或改变游戏逻辑。

实现只用整数、预打包查表和对齐批量显存写入，不在运行时做浮点计算或逐像素除法。
12 KiB 三相位输出查表加 512 字节位展开表在 PC 上生成并置于只读区，无初始化或堆分配；
复用原有 1,920 字节源显存缓存和 9,600 字节屏幕影子，行工作数组 44 字节、审计数组 144 字节，
另加 20 字节绘图批次状态。这些是显式数据，不包含编译器生成的其他栈帧。

独立字节写入立即重采样依赖它的最多三条目标行，并修复左右边缘的依赖像素。
已证明源不与 LCD 重叠的多行位图、已快照的位图及字形则在该次绘图调用内合并插值行，
完成后立即输出到 framebuffer，**不等 present、下一帧或输入查询**。
LCD 重叠/未知读副作用路径保留逐项顺序；原始 RAM 修改仍由两遍屏幕审计修复，
先采集全部源行，再重采样，避免读到旧的下一行。游戏内部按键采集检查点保留。

2026-10-13，用实际 9288T 生成的运行库对象执行 S1C33 CPU 隔离对照。
输入为交替反相的纹理，避免测到静态画面的无变化跳过；每种运行 1 次和 33 次，
差值除以 32 排除启动。位图使用普通 RAM 中经过验证的非重叠源，直接调用实际 `native_picture`。

| 操作 | 1.5× 最近邻 CPU 周期 | 1.5× 双线性 CPU 周期 | 局部开销倍数 |
| --- | ---: | ---: | ---: |
| 不变画面的显存审计 | 84,394 | 95,848 | 1.14× |
| 159×96 完整位图调用 | 128,011 | 344,722 | 2.69× |
| 16×16 图块调用 | 7,442 | 17,354 | 2.33× |
| 96 个独立整行写入（不合批） | 126,440 | 573,244 | 4.53× |
| 16 个独立小行段（不合批） | 7,106 | 26,026 | 3.66× |

最初 768 字节紧凑查表实现的独立整屏行写入为 817,815 周期；预打包、交错采样与
调用内合批降低重复移位、访存和重采样成本。独立行/像素频繁修改仍比批量位图更昂贵。
上述是局部 CPU 周期，不含真实外部内存等待、固件竞争或完整游戏执行，**不是实机 FPS**。
各 CPU 输出均与独立逐像素四点参考一致，宿主回归另外覆盖裁剪、重叠、字形、折行、
原始 RAM 修改和 GUI 覆盖恢复。它们不能替代真机运行验证。

复现脚本：`scripts/benchmark_9288t_framebuffer.py --changing-input --include-tiles --include-pictures`
并传入实际 `--runtime-object`、`--toolchain`、`--emulator`、`--output`、`--display-scale`。
两个模式分别构建，不能把同一个对象当作另一种缩放测试；脚本会验证目标像素的独立参考。
固定模式也保留用于看无变化跳过，但不能用其结果代表动态动画成本。

退出后的 `NATIVE.LOG` 增加 `display_filter=bilinear_4gray`、`linear_rows`、
`linear_unchanged_spans`、`linear_batches`，结合原有 picture/text/surface 阶段耗时做真机归因。
建议同一游戏、同一剧情、相同操作分别运行最近邻和线性 EXE；崩溃追踪保持关闭。
线性灰阶能平滑斜线，也可能让细文字发虚；它确实有额外绘图成本，因此默认仍为 1×，
性能优先时选点对点或最近邻。是否有可接受的整体速度必须由对应固件的真机对照决定。

### T-ROW-AUDIT-1：行批量输出与物理屏幕审计

2026-10-10，以下是原 1.5× 适配层的局部优化记录（现保留为可选模式），
不修改游戏逻辑、动画 Timer 参数、输入队列或 9288 绘图路径：

- 连续行段每四个 guest 字节合并为三个对齐的 32 位 framebuffer 写入。非对齐前缀/尾部
  及独立 LCD 字节仍精确写入对应区域；纵向 2/1 行展开、隐藏像素、折行及遮罩保持一致。
- 独立字节输出使用常量位移，不再由 C 的可变位移生成内部移位循环；计数按行段累计，
  不在每个宿主字节上更新性能计数器。
- 增加 9,600 字节、4 字节对齐的 `.noinit` 预期物理画面缓存。每次正常绘图立即同时
  更新缓存和实际显存，**不是等到 present 才显示**，也不是声称开启了双缓冲。
- 审计先检查 guest RAM 与上一版的差异，仅重新展开变化的行，再比较 2,400 个物理字；
  只恢复不一致的字。仍检测无通知的 GUI/DMA 覆盖以及绕过映射的 guest RAM 修改。
- 审计间隔从完成时计起，避免慢审计自身占满 250 ms 后，在下一次取键时立即再做一次。
  `MSG_PAINT` 显式失效保持立即恢复，游戏 Timer 的硬件时间不改。

#### 可复现的 CPU 局部对照

`scripts/benchmark_9288t_framebuffer.py` 使用真实构建出的新旧 S1C33 运行库对象，
在预览 CPU 中执行相同的审计或整屏行段工作，不启用系统 IRQ/外设实时时钟。
分别跑 1 次和 33 次，相减得到 32 次工作的周期，排除固定启动/初始化成本。
微程序检查完成次数、HALT、异常和未知访存，保存 framebuffer 哈希核对输出一致。
它不包含 GAM、ROM 或游戏特例。

| 32 次相同工作 | 旧实现 CPU 周期 | T-ROW-AUDIT-1 CPU 周期 | 局部周期减少 |
| --- | ---: | ---: | ---: |
| 静止画面整屏审计 | 12,664,841 | 2,700,617 | 78.7% |
| 159×96 整屏按行绘图 | 10,834,856 | 3,480,488 | 67.9% |

两项新旧 framebuffer SHA-256 完全一致。这是 CPU 微程序的局部工作量对照，
**不是游戏帧率、真机墙钟加速或整个游戏提高 3～5 倍的结论**。
当前模拟器执行 CPU 的速度与外设实时推进速度不同，LCD 面板的约 60 fps 不能当游戏 FPS。
另外观察到官方版运行时固件通过 HSDMA 向 LCD VRAM 搬运 9,600 字节，
但本版尚未改用 DMA；DMA 占用、固件交互及局部绘图语义需要独立验证，不凭此观察强行接管通道。

PERF 日志 `build=T-ROW-AUDIT-1` 新增 `framebuffer_shadow_bytes`（固定 9,600）、
`framebuffer_audit_words`、`framebuffer_repaired_words`、`t_packed_groups`。
`framebuffer_bytes` 仍只统计物理 framebuffer 写入，不包含缓存写入；
`presents/submissions` 仍是审计次数，不是游戏帧数。

### 启动异常的实际原因与修复

1. **CMP 扩展形式。** 模拟器不接受部分 `EXT + register CMP`，后端改用
   `EXT + immediate CMP`；完整常量及比较语义保持不变。
2. **超过两次 EXT。** 32 位掩码（如 C6502 栈指针更新使用的 `0xffffff00`）
   曾被按寄存器形式拆成三次 EXT。S1C33 最多允许两次，模拟器在
   《伏魔记》生成函数 `c6502_game_fn_1828d` 中明确报错。所有常量现在使用
   末指令含低 6 位的立即数形式，最多两次 EXT；ADD/SUB 无符号、逻辑/LD/CMP
   有符号，并正确处理 19 位正数的符号扩展边界。寄存器形式超 26 位直接拒绝。
3. **LD 标志位差异。** S1C33000 指令手册规定 LD 不改变 N/Z/C/V；当前
   Dream9288T CPU 对立即数/内存加载却更新 N/Z。独立微程序复现了
   `CMP → LD → JRLT` 走错分支，《魔塔》的 Bresenham 菜单边框因此陷入死循环，
   还未进入游戏取键。9288T 构建在 C 编译后的汇编阶段，仅给 CMP 到条件跳转之间
   的相关加载添加完整 PSR 保存/恢复；正确调整 SP 相对地址，保留 R0 结果，
   不使用固件保留的 R15，不关闭优化或修改模拟器二进制。

该 PSR 保护在遵循手册的真机上也保持语义；上述启动修复阶段的主运行库及窗口入口有
17 处保护，体积增加 336 字节；当时 9288 C 编译路径不加此加载兼容处理。
测试同时覆盖加载目标 R0、字节/半字/字 SP 寻址、EXT 绑定、栈恢复与完整常量，
可设置 `A9288_TEST_CLANG` / `A9288_TEST_C33EMU` 执行实际 CPU 微程序回归。

后续《魔塔》首次战斗真机重启另定位到 LLVM `ADJFI` 帧地址展开覆盖比较标志，
不是上述模拟器 LD 差异。转换器已为全部机型增加通用帧地址保护，并修正 EXT 的
SP 字节位移补偿；根因、实际绘图对象回放及验证边界见
[代码生成正确性记录](compiler-correctness.md)。

### 退出收尾修正

9288T 真机反馈《魔塔》退出后重启，检查发现两个生命周期风险：
输入释放消息循环可以先处理 `MSG_CLOSE` 并消费 Quit，旧 App_Main 却仍无条件重新关闭、等待 Quit；
另有从 9288 沿用的桌面两消息边界恢复，会在退出应用的栈上读取、分派 launcher 消息。
后者不是官方 T 程序的退出流程。

运行库现在记住本窗口的关闭状态，重复关闭幂等，已关闭且消费 Quit 时不再等待第二次 Quit；
启动期间提前关闭也不再进入游戏，`CreateMainWindow` 同时识别 0 和 SDK 的 `HWND_INVALID`。
T 清理本应用窗口后恢复备份画面并返回宿主，不处理 launcher 的消息，也不读取那条 9288 恢复路径的 DMA 状态。
9288/S/600 的既有桌面恢复保留，其他状态保护与游戏内部私有输入不变。

退出前开启 D 后，追踪会继续到宿主清理完毕，详见 [崩溃追踪](crash-tracing.md)。
这能区分游戏没有返回、释放输入卡住、Destroy/窗口清理失败或释放资源失败；原来的
`returned_from_game` 仅能证明游戏返回，不能证明后续正常返回桌面。

回归覆盖正常游戏返回、释放输入期间提前关闭、重复 CLOSE、启动期关闭、创建返回 -1，
检查只 Destroy/Cleanup 一次、释放资源与桌面备份、还原画面且从不处理 T 的 launcher 消息。
实际生成的 T `App_Main` 对象也在 S1C33 CPU 隔离测试中完成这五种情形，SP 与保留的 R15 恢复，
无异常或未知访问。该测试的 SDK 服务是 mock，不包含真实固件调度、按键中断或文件系统。
**已修正上述代码风险，但它们是否就是本次真机重启的根因，仍需新 EXE 复测及退出日志确认。**
