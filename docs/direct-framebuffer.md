# 原生运行库直接 framebuffer 映射

## 为什么修改

原 A 系列的 `SysPicture` 修改 LCD 显存，不需要另一个 `Present` API。
此前移植层在部分区域绘图后每隔约 23.4 ms 提交整屏，会在地图重绘中途重复转换
并输出 19,200 字节。绘图顺序来自游戏，定时提交与 2× 整屏转换的成本则来自移植层。

`DIRECT-FB-1` 保持游戏 LCD RAM 的原始布局，每次可见显存写入立即扩展到
`0x003c0000` 的相应位置，不等待输入、GUI Timer 或完整一帧。不是把两块内存设置
为同一指针：A 系列的折行 1-bpp 数据与 9288 的线性 2-bpp 数据格式不同，仍需转换。

## 路径和兼容性

- `guest_write` 和 `physical_write` 接入统一映射，覆盖直接地址、bank 别名与 DATA 通道。
- S1C33 间接写快速路径对 `$0400..$1000` 转入带映射的处理；普通 RAM 仍走原生快路径。
- 映射仅处理其中 1,920 个可见字节，跳过填充；保留 `$0FF3`、`$1000` 和第 65 行的布局。
- 每个显存字节展开为两行宿主像素；处理横向一像素居中产生的跨字节边界，保留隐藏的
  第 160 个游戏像素在 RAM 中，不把它画到屏幕上。
- 图形、字形、清屏、反色和背景恢复使用同一写入路径。离屏 `SysPictureDummy` 只改
  目标 RAM，除非调用者明确让目标与真实 LCD 存储重叠。
- 保留游戏可读写的 LCD RAM：读回、保存/恢复、重叠复制和游戏自绘仍观察原来的数据。

这不提供垂直同步或整图原子显示：LCD 控制器可以扫描到绘制中的画面，与原直接绘图
模型一致。减少的是重复整屏转换/写入，不宣称完全消除逐块感或撕裂。

## 系统覆盖与统计

系统 GUI/中断仍可能覆盖物理屏幕。启动及显式恢复可以调用 `c6502_native_present`；
输入/等待路径约每 250 ms 审核一次物理画面，`MSG_PAINT` 失效时不等待这个间隔。
审核将实际 framebuffer 与游戏 LCD 对照，仅写不一致的宿主字，不依赖影子缓存断言
屏幕未被系统修改。绘图 API 内不再因刷新计时器到期而调用整屏提交。

`NATIVE.LOG` 使用 `A9288 NATIVE PERF 3 / DIRECT-FB-1`：

- `mapped_lcd_bytes`：即时映射的可见 LCD 字节写次数，包含同值写入。
- `framebuffer_bytes`：直接映射与恢复合计的宿主 framebuffer 写入字节数。
- `repair_checks`：输入/等待路径的画面审核次数。
- `presents/submissions`：保留字段，表示整屏对照/恢复调用，**不再代表游戏帧率**。
- `present_ticks`：整屏对照/恢复耗时；`graphics_ticks` 包含绘图 API 内的即时映射成本。
  游戏原生代码直接写显存产生的成本不归到 `graphics_ticks`，不能用它作为全部输出耗时。
- `picture_frame_commits`：完整 `SysPicture` 调用数，仅作诊断，不再触发额外提交。

对齐的 16×16 tile 回归会写 32 个 LCD 字节，对应 320 字节宿主写入，而非触发一次
19,200 字节整屏写入。这不是 60 倍运行速度的测量，仍需真机同场景日志对比。

## 验证

无商业游戏的宿主测试直接编译实际 C 映射函数，覆盖整个 LCD 地址范围、边界上的
全部字节值、任意顺序写入、bank/DATA 别名、离屏合成、文字、位图、背景恢复、时钟
不推进时的连续动画，以及未通知应用的 GUI 覆盖恢复。保留原固件绘图结果等价测试。
模拟器使用用户自备《魔塔之怀旧终曲》验证；生成游戏和调试内存不进入 Git 或分发包。

## BLIT-ROW-1：公共位图行融合

2026-09-06，用户确认 `INPUT-POLL-1` 真机按键正常，退出没有桌面残留动作。
这轮不修改输入、退出或 Timer 语义，只优化编译器公共图形运行库。

该次《伏魔记》日志的 28,234 个 CTM tick = 110.289 秒，独占阶段合计一致：

- `picture` 6,956 tick（24.64%），完整 `SysPicture` 常为 25–26 tick（97.7–101.6 ms）。
- `other` 17,039 tick（60.35%），包含原生游戏、未细分辅助函数、系统和探针开销；
  不能把它全部当成计算或磁盘读取。
- `present_ticks` 1,292 tick 是原有重叠计数，不可再与独占阶段相加；
  215 次 `presents` 是物理画面审核，不是游戏帧数。

优化原理：普通图片一次证明源不与 LCD 重叠；能连续映射的 RAM/游戏资源直接读指针，
跨不连续 bank 则保留逐字节取源。字节对齐行只计算一次折行基址，顺序合成相邻字节的
宿主边界，只修补行段最右侧邻居。游戏 LCD RAM、隐藏像素和边缘遮罩仍保持一致。
单字节 ROM 特殊遮罩、LCD 自重叠、DATA/I/O 和地址回绕继续走原访问顺序。
非对齐 `flag=0` 行继续使用上一版的逐字节遮罩/移位实现；`flag=1` 按固件语义本就
恢复整字节，仍可使用行融合。完整图片和常见对齐 tile 不受此限制。

行内持续直接写 framebuffer，不等待输入或 `present`；行结束采样按键，最多间隔
20 个客机字节（未融合路径仍按原 32 字节检查），保留纯轮询实现。仅使用 20 字节
临时行缓冲，没有增加持久图片缓存或 IRQ/裸机切换。

确定性的写入量变化（**不是测得的整机速度提升**）：

- 159×96 整屏：19,008 → 15,360 个宿主写入字节（减少约 19.2%）。
- 对齐 16×16 tile：320 → 288 字节（减少 10%）。
- 还省掉每字节的通用访存、LCD 逆映射和内部邻居读改写，其真机耗时收益待对照日志。

新增轻量计数：`lcd_span_rows/bytes`（行融合量，含字形），
`picture_direct_bytes`（直接资源指针读取量）、`picture_staged_bytes`（非连续源暂存量）、
`picture_ordered_calls`（保留原顺序的绘图调用，包含单字节特殊路径）。计数不增加逐字节时钟读取。
后续对照请使用相同片头/操作路径，比较 `sample` 的完整图片 `draw_ticks` 和间隔，
而不是不同游玩长度的总体“帧率”。即使完全消除 picture 的耗时，此次路径的理论上限
也只有约 1.33×，剩余大头仍须继续细分 `other`。

### 验证范围及未采用的实验

- 完整测试 70 项通过（含真实固件 ABI/绘图对照、1,200 组源地址/矩形/flag
  差分，覆盖不连续 bank、MMIO、回绕及 LCD 源重叠）。
- 最终《伏魔记》《三国霸业》均已用 9288 SDK 构建；游戏本身的
  `game-combined.o` 与 INPUT-POLL-1 逐字节相同，只更新公共运行库。
- 曾尝试将非对齐行先变移位到临时行，再使用行融合。宿主等价测试通过，但
  S1C33 模拟器在跳过片头时异常。追踪看到反复在 `blit_packed_row` 的变移位
  循环附近进入系统 IRQ，最后系统 `reti`（`$0216960E`）返回 `$00000008`。
  这不足以断言是模拟器、编译器或系统哪一方的问题，该新增分支**不在交付版本中**。
  保留原非对齐循环后的最终版本已越过同一片头跳过点并进入地图/菜单。
  没有通过修改系统中断、自动关机设置或模拟器源码绕过验证。
