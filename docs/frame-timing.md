# 原生程序帧间隔与耗时日志

## OTHER-PROFILE-1：原生调用边界与辅助函数诊断

2026-09-06：BLIT-ROW-1 真机开头 16 次整屏绘制均值从 25.125 降至 3.5
CTM ticks（98.1 → 13.7 ms），第 1 到第 16 次整屏完成间隔为 14.80 → 13.48 秒。
此段约 1.10×，不是整局 7.2×。新日志 picture 占 6.9%，other 占 74.0%；
游玩路线不同，整局占比不是固定负载基准。

转换时添加 `--profile-other` 生成 `[A9288 NATIVE PERF 6]` / `OTHER-PROFILE-1`。
默认仍是 BLIT-ROW-1，不插入额外探针。游戏原生目标文件、普通 RAM 汇编快路径、
绘图、按键、Timer、IRQ 和退出协议均不改变。日志仍退出时一次性写入
`A:\NATIVE.LOG`，上一会话为 `A:\NATIVE.BAK`，没有运行中写盘。

- `profile_bridge`：公共 API 每次计时；辅助函数统计所有进入 C 慢桥的调用，
  首次计时，之后伪随机间隔 1～127 次（均值目标 64）。汇编快路径和内联/outline
  不在该计数中。samples 不等于 calls 时，ticks 仅是实测样本合计，不乘 64
  冒充真实总耗时；抽样可能有偏差。
- `profile_gap_other_ticks`：测量边界间的 OTHER，包含原生游戏、未抽中/内联的
  辅助函数、系统中断和探针开销，**不是纯游戏 CPU 时间**。
- `profile_measured_bridge_other_ticks`：测量桥接中属于 OTHER 的部分，与 gap
  相加应等于 phase,0。`profile_other_match=1` 仅是记账校验；图形/GetMsg 等
  已分类耗时不会再次计入 OTHER。
- `profile_edge`：上一个测量返回点 → 下一个测量调用点，非零区间数、OTHER
  总和及最大值。256 固定槽、最多探测 4 槽；满表未收录的区间数/ticks 单列，
  不声称无损保留所有热点。
- `profile_spike`：另外保留最长 16 个至少 32 ticks 且 OTHER 非零的区间。
  `profile_keygap` 保留最长 16 个原有按键扫描空档。只记录端点，不是完整调用栈，
  不额外扫描按键或改变消费/重复/去抖。
- `profile_clock_reads`：新增完整 CTM 读取次数。统计本身及系统中断有开销；
  此版用于归因，不用它相对 BLIT-ROW-1 的速度差判定性能回归。

桥接汇编保存 R8 后、PUSHN 之前从确定的 SP+4 取原生返回 PC，用 GNU33 第三
参数 R8 传给探针。不扫描栈内存、不改 R15 或 ISR。返回 PC 不是客机 PC；
尾调用桥接的返回点可能在上层调用者，不能把区间耗时算成该函数独占耗时。
边界统计还不能精确拆分系统中断或无调用的内联循环，定位后应定点细分。

转换附带该 EXE 的 `.profile-symbols.json`（EXE/GAM SHA256、ELF 函数范围）。
离线运行 `python scripts/analyze_native_profile.py NATIVE.LOG 游戏.profile-symbols.json`
解析调用位置到 `GAM+0x...`，不要混用其他构建符号。用户只需提供完整日志，
开发侧保留这次符号表即可分析。

`[A9288 NATIVE PERF 5] / build=EXIT-INPUT-2` 用于《伏魔记》《三国霸业》等
原生输出的共同诊断。保留游戏等待参数、单 pending 位和 framebuffer 直绘策略。
INPUT-FAIR-1 对持续过载时的消息仲裁增加按键公平性，详见 input-short-taps.md；
不是 CPU 提速补丁，不保证测试版比非统计版快。

## 时间单位和可信度

- 所有 `ticks`、`at`、`gap`、窗口时间和 `elapsed` 都是 CTM 的 256 Hz 计数；
  **毫秒 = ticks × 1000 / 256**，不是 ticks = ms，也不是 GUI Timer 的 25 ms。
- 单次调用小于约 3.906 ms 时可能记作 0；这不是零成本。
- 没有引入另一套独立时钟。因此它能区分执行/等待分布，不能仅凭自己证明
  CTM 的实际频率正确；可同时用手机秒表计时，模拟器时间不用于真机性能结论。
- `phase_elapsed_match=1` 表示互斥分类之和与会话时长相等，仅为记账校验。
  `timing_invalid_deltas` 非零表示发现倒退式采样，不能用该会话作速度结论。

## 互斥耗时分类

`phase` 行：`id,calls,ticks,max_call_ticks,10个耗时直方图区间`。

| id | 类别 | 口径 |
|---|---|---|
| 0 | other | 原生游戏、未插桩的运行库、系统中断/调度和部分统计开销；**不是纯 CPU 计算** |
| 1 | picture | SysPicture / SysPictureDummy，含内部资源读取、合成、映射输出和补采样 |
| 2 | text | SysAscii / SysPrintString，包括字模处理与输出 |
| 3 | shape | 线、矩形、清屏、反色、像素 API |
| 4 | surface | 保存/恢复屏幕 API |
| 5 | memory | 公共 memcpy / fillmem；直接原生访存仍在 other 中 |
| 6 | getmsg | 整次 GuiGetMsg，含等待、按键采样和屏幕修复 |
| 7 | getkey | 整次非阻塞 SysGetKey |
| 8 | dialog | 原生消息框/确认框整个调用，含绘制和等用户操作 |

这九项互斥，可求和。旧 `graphics_ticks/present_ticks/wait_ticks/msgbox_ticks`
是嵌套子统计，**不要再与上述 phase 相加**。旧 waits 是窗口查询次数，
不能拿它代表游戏的完整等待时长。Dialog 耗时大可能只是用户思考，
GetMsg 耗时大可能是游戏设计的等待，不意味着这两个函数值得盲目优化。

`window` 保留最近 64 个完整的 10 秒窗口，外加最后一个未满窗口；
长 API 调用按真实时间切开，不全部计到结束的窗口。列名直接写在日志里。
这样能分开看片头、菜单和地图阶段，避免整局平均数掩盖热点。

## 动画/显示观测

有两条互相独立的 `interval` 序列和 `sample` 记录：

1. `kind=1`：覆盖整个 159×96 视区的 SysPicture **完成时刻**。
   不是 LCD vsync，不保证每次图片内容都不同，也不是游戏所有动画的统一帧边界。
2. `kind=2`：自上次输入检查以来发生 LCD 映射写入，在下一次输入/对话 API
   入口记录一个显示批次。适合地图 tile 游戏的观测，但**不是把 tile 当成帧**，
   也不保证游戏完整地图已经画完。直接 framebuffer 在这些记录前就已可见。

每种序列的首事件 `gap_valid=0`，不能当成从启动到第一帧的动画间隔；
之后 `gap=0` 可以是同一个 CTM 刻度内的合法两次输出。
`interval` 保存全会话的样本数、间隔数、最小/最大/总间隔、十档直方图：
0、1–2、3–4、5–8、9–16、17–32、33–64、65–128、129–256、257+ ticks。

`sample` 保留最初 32 条和其后的最近 96 条事件，带全局递增序号，按时间顺序输出。
中间被省略的数量会明确写出；不会声称这是全会话无损逐帧 trace。
每条包括间隔、当前绘图调用耗时、Timer reload/number，以及**同种事件间**的
九类耗时差值和 Timer 计数差值。首条的差值来自会话起点；输入批次的 draw_ticks=0
表示没有对应的单次完整绘制 API，不能据此说绘制免费。
number=0 可表示硬件 Timer 禁用或 RAM 配置为零，不能盲目乘作目标间隔。

## Timer 观察

- `timer_steps`：按时间应产生的 A 系列 WM_TIMER 次数。
- `timer_messages_delivered`：实际由 GuiGetMsg 返回的次数。
- `timer_coalesced`：同一个 pending 位已占用、或一次跨过多个周期而合并的次数。
- `timer_burst_max`：一次定时推进产生的最大消息数。
- `timer_update_max_gap_ticks`：Timer 开启时，两次推进之间的最大 CTM 间隔。

原固件是单 pending 位，不能为让数字好看擅自换成补发队列。对话框等路径也会
清除 pending 位，游戏可能直接改 RAM，所以 generated 与 delivered 不必简单相等。
这些是观察计数，不能把所有差额都归因于绘图。

## 如何选择下一步优化

- picture/text/memory 占比高：优化对应公共实现，再做等价测试。
- other 高：需要进一步定位原生游戏/未计时运行库，不把它直接叫解释器成本。
- GetMsg 等待长、绘制短：核对原 GAM 等待参数和事件计数，不先改 CPU 引擎。
- 绘制长且 coalesced 增长：绘制成本与消息合并共同拖慢动画。
- 平均间隔不高但 max/直方图尾部大：优先查卡顿尖峰；输入采样 gap 也同时看。

本改动的验证是日志结构、计数/窗口边界、32 位时钟回绕、既有固件等价和编译验证；
真实速度与卡顿归因仍以本次真机日志为准。

## 2026-09-06 输入不响应反馈与有界统计

用户最初描述地图移动数步后死机，随后明确：动画仍继续播放，《三国霸业》也有
同样的按键无响应。这应按输入停滞调查，不是已证实的 CPU 停机。
普通模拟器走图已越过用户指出的位置，未复现自然发生的输入停滞。
对实际 GuiGetMsg 强制每次都有 pending Timer 后，复现了按键无限饥饿；
公共输入修正和新计数器见 input-short-taps.md。

同时保留一个不改变游戏语义的统计器改进：

- 原统计器按时间差循环填 10 秒窗口，大幅向前跳时会生成几十万个随后被覆盖的窗口。
  现在直接跳过必然淘汰的完整窗口，只处理首个部分窗口、最后 64 个完整窗口和尾部。
  保留窗口的时间、分类与环形顺序与原算法一致；`timing_window_fast_forwards`
  表示跳过的窗口数。这不是丢掉全会话分类总耗时。

截断实验，不把它作为这次输入问题的解决方案交付。INPUT-FAIR-1 不含该截断，
没有修改时钟采样、键盘中断控制、图形参数、游戏原生代码或游戏等待参数。
